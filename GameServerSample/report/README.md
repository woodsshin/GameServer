# 부하 테스트 리포트 — C++ 비동기 게임 서버

실제로 서버를 빌드하여 실행하고, 최대 1,000개 동시 접속을 시뮬레이션한 부하 테스트를 수행한
결과를 정리한 문서입니다. 모든 수치는 실측치이며, 추정치나 이론값이 아닙니다.

## 1. 테스트 환경

| 항목 | 값 |
|---|---|
| CPU | 1 vCPU (Intel Xeon @ 2.10GHz) |
| 메모리 | 4 GB |
| OS | Ubuntu 24.04 |
| DB | MariaDB 10.11.14 (libmysqlclient 8.0 호환) |
| 컴파일 옵션 | `-O2 -Wall -Wextra -pthread` (경고 없이 빌드 확인) |
| 부하 생성기 | Python 3.12 / asyncio 기반 자체 제작 클라이언트 (`tools/load_test.py`) |

> **중요**: 본 테스트는 **1 vCPU 환경**에서 수행되었습니다. 실제 배포 환경(4~16 vCPU 등)에서는
> IO worker와 DB worker가 여러 코어에 물리적으로 분산되어 처리량이 코어 수에 비례해 크게
> 개선될 것으로 예상됩니다. 이 리포트의 목적은 "얼마나 빠른가"보다 **"어디가 병목인가를
> 실측으로 증명하는 것"**입니다.

## 2. 테스트 방법

`tools/load_test.py`가 실제 클라이언트 프로토콜(`PacketDef.h`와 동일한 바이너리 포맷)로
서버와 직접 통신하며 아래 시나리오를 수행합니다.

```
접속 → 회원가입(C2S_REGISTER) → 로그인(C2S_LOGIN) → 채팅 3회(C2S_CHAT_MESSAGE) → 하트비트 → 종료
```

- 서버가 반환하는 실제 응답 패킷(`S2C_REGISTER_RESULT`, `S2C_LOGIN_RESULT`,
  `S2C_CHAT_BROADCAST` 등)을 파싱해 성공/실패를 판정합니다. 단순 TCP 연결 성공이 아니라
  "회원가입이 실제로 DB에 반영되었는가"까지 검증합니다.
- 동시 클라이언트 수를 100 / 300 / 600 / 1,000명 단계로 늘려가며 각 단계마다 접속 성공률,
  단계별 응답 지연시간(p50/p95/p99), 처리량(req/sec)을 측정했습니다.
- 서버 프로세스의 CPU 사용률, 메모리(RSS), 오픈 파일 디스크립터 수를 1초 간격으로 함께
  기록했습니다(`resource_usage.csv`).

## 3. 핵심 결과 요약

### 3.1 접속(TCP/epoll) 계층은 1,000 동시 접속까지 문제없이 처리

| 동시 접속 수 | 접속 성공률 | 접속 지연 p50 | 접속 지연 p99 |
|---:|---:|---:|---:|
| 100 | 100% | 0.30 ms | 1.04 ms |
| 300 | 100% | 0.24 ms | 0.66 ms |
| 600 | 100% | 0.26 ms | 1.88 ms |
| 1,000 | 100% | 0.25 ms | 1.75 ms |

Accept 스레드와 epoll 기반 IoWorker는 클라이언트 수가 늘어나도 접속 성공률과 지연 시간이
전혀 저하되지 않았습니다. **설계 의도대로 네트워크 계층은 병목이 되지 않았습니다.**

### 3.2 채팅 브로드캐스트도 동시접속 규모와 무관하게 항상 즉답 수준

| 동시 접속 수 | 채팅 왕복 p50 | 채팅 왕복 p99 | 응답 확인율 |
|---:|---:|---:|---:|
| 100 | 0.09 ms | 3.84 ms | 100% |
| 300 | 0.09 ms | 4.64 ms | 100% |
| 600 | 0.08 ms | 4.34 ms | 100% |
| 1,000 | 0.08 ms | 4.17 ms | 100% |

`SessionManager`의 `shared_mutex` 스냅샷 패턴이 의도한 대로 동작하여, 브로드캐스트 처리
시간이 접속자 수 증가와 사실상 무관했습니다.

### 3.3 회원가입/로그인은 동시 접속이 늘어날수록 지연이 뚜렷하게 증가 (병목 지점)

**시나리오 A — 원본 그대로 (SHA-256 스트레칭 10,000라운드, IO worker 자동/DB worker 4개)**

| 동시 접속 수 | 회원가입 성공률 | 회원가입 p50 | 회원가입 p99 | 로그인 p50 | 로그인 p99 |
|---:|---:|---:|---:|---:|---:|
| 100 | 100% | 505 ms | 969 ms | 685 ms | 970 ms |
| 300 | 100% | 2,422 ms | 4,866 ms | 4,338 ms | 4,936 ms |
| 600 | 100% | 5,155 ms | 9,727 ms | 9,066 ms | 9,844 ms |
| 1,000 | **92.3%** | 7,650 ms | 14,878 ms | 14,185 ms | 14,994 ms |

1,000명 구간에서는 응답 대기 15초 타임아웃을 넘겨 실패하는 클라이언트가 발생했습니다
(923/1,000 가입 성공, 로그인은 564건만 15초 내 완료).

**결정적 관찰: 회원가입 처리량이 동시 접속 수와 무관하게 항상 27.5 req/sec로 고정됨**

| 동시 접속 수 | 회원가입 처리량 |
|---:|---:|
| 100 | 27.55 req/s |
| 300 | 27.17 req/s |
| 600 | 27.59 req/s |
| 1,000 | 27.54 req/s |

동시 접속자를 10배로 늘려도 초당 처리 건수가 전혀 늘지 않는다는 것은, 시스템이 이미
어딘가에서 **포화(saturation)** 상태에 도달했고 이후로는 대기열만 길어진다는 뜻입니다.
이 시점에서의 서버 CPU 사용률은 평균 65.5%, 최대 77.5%(1코어 기준)로, 이미 CPU 자원이
한계에 가까웠습니다.

## 4. 원인 분석: 비밀번호 해싱 스트레칭이 CPU 병목의 실체

`PasswordHash.h`의 `HashPassword()`(SHA-256 + salt + 10,000라운드 스트레칭)를 단독으로
벤치마크한 결과입니다.

| 스트레칭 라운드 | 1회 해싱 평균 소요 시간 | 이론상 단일 코어 최대 처리량 |
|---:|---:|---:|
| 10,000 (원본) | 15.76 ms | 약 63 req/s |
| 1,000 | 1.53 ms | 약 654 req/s |
| 100 | 0.15 ms | 약 6,515 req/s |

라운드 수와 처리 시간이 거의 정확히 비례합니다. 회원가입/로그인 요청마다 이 해싱이
1회씩 동기적으로 실행되므로, DB worker 스레드 수를 아무리 늘려도 **물리 코어가 부족하면
해싱 자체가 상한선이 됩니다.**

### 검증: IO/DB worker 수를 늘려도 개선되지 않음 (CPU가 병목이라는 증거)

**시나리오 B — IO worker 8개, DB worker 16개로 강제 확장 (동일 1 vCPU 환경)**

| 동시 접속 수 | 회원가입 성공률 | 회원가입 p50 | 로그인 p50 |
|---:|---:|---:|---:|
| 100 | 100% | 514 ms | 661 ms |
| 300 | 100% | 2,443 ms | 4,760 ms |
| 600 | 99.5% | 5,309 ms | 9,739 ms |
| 1,000 | 89.4% | 7,628 ms | 14,358 ms |

worker 스레드를 4배(IO 1→8) ~ 4배(DB 4→16) 늘렸음에도 시나리오 A와 사실상 동일한 결과입니다.
**worker 수를 늘리는 것은 "동시에 계산할 CPU가 있을 때"만 효과가 있으며, 1개뿐인 물리 코어
위에서는 스레드를 아무리 늘려도 처리량이 늘지 않는다는 것을 실측으로 확인했습니다.**

### 대조군: 해싱 라운드를 1,000으로 낮추면 (원본의 1/10 비용)

**시나리오 C — 스트레칭 1,000라운드, 나머지 조건은 시나리오 A와 동일**

| 동시 접속 수 | 회원가입 성공률 | 회원가입 p50 | 로그인 p50 | 회원가입 처리량 |
|---:|---:|---:|---:|---:|
| 100 | 100% | 3.0 ms | 2.9 ms | 48.7 req/s |
| 300 | 100% | 8.8 ms | 9.2 ms | 142.4 req/s |
| 600 | 100% | 295 ms | 337 ms | 146.6 req/s |
| 1,000 | **100%** | 544 ms | 592 ms | 148.2 req/s |

같은 1 vCPU, 같은 동시 접속 규모에서 서버 CPU 평균 사용률도 65.5% → **17.4%**로 크게
낮아졌습니다.

### Before / After 비교 (1,000명 동시 접속 기준)

| 지표 | 원본 (10,000라운드) | 개선 (1,000라운드) | 변화 |
|---|---:|---:|---:|
| 회원가입 성공률 | 92.3% | 100% | +7.7%p |
| 회원가입 지연 p50 | 7,650 ms | 544 ms | **약 14.1배 감소** |
| 로그인 지연 p50 | 14,185 ms | 592 ms | **약 24.0배 감소** |
| 회원가입 처리량 | 27.5 req/s | 148.2 req/s | **약 5.4배 증가** |
| 서버 CPU 평균 사용률 | 65.5% | 17.4% | 대폭 감소 |

처리량이 라운드 감소 비율(10배)만큼 정확히 오르지 않은 이유는, 회원가입 요청 안에는
해싱 외에도 중복 아이디 확인(SELECT)과 계정 생성(INSERT) 쿼리가 함께 들어있어 그만큼의
고정 비용이 남아있기 때문입니다. 이는 실제 병목 지점을 정확히 짚어낸 결과이자, 남은 병목
(쿼리 왕복 비용)의 크기도 함께 드러내 줍니다.

## 5. 결론 및 권장 사항

1. **네트워크/동시성 설계(epoll, shared_mutex, worker 분리 구조)는 검증됨.** 접속과 채팅
   브로드캐스트는 1,000 동시 접속까지 매우 안정적이며 병목이 아닙니다.
2. **현재 병목은 순수하게 CPU 바운드인 비밀번호 해싱 비용(10,000라운드 SHA-256
   스트레칭)입니다.** 이는 DB 쿼리, 네트워크, 락 경합의 문제가 아니라는 것을 worker 수
   증량 테스트와 라운드 축소 대조군 테스트로 교차 검증했습니다.
3. **실무 개선 방향**:
   - README에 이미 명시된 대로 bcrypt/Argon2로 교체하는 것이 근본 해결책입니다. 이들
     라이브러리는 워크팩터를 조정 가능하며, 특히 Argon2는 병렬화·메모리 하드니스가
     설계에 포함되어 있어 동일 보안 강도 대비 CPU 점유 패턴이 더 예측 가능합니다.
   - 현재 구조(SHA-256 스트레칭)를 유지해야 한다면, 라운드 수를 보안 요구 수준에 맞춰
     하향 조정(예: 10,000 → 2,000~3,000)하는 것만으로도 큰 폭의 개선이 가능함을 확인했습니다.
   - 근본적으로는 **다중 코어 환경 배포 시 DB worker 스레드가 각 코어에서 병렬로 해싱을
     수행**하므로, 이 병목의 체감 영향은 코어 수에 거의 반비례하여 줄어들 것으로 예상됩니다
     (예: 8 vCPU 환경이라면 이론상 지금의 1/8 수준까지 개선 가능). 이는 이번 리포트의
     범위를 벗어나므로 다중 코어 환경에서의 재측정을 권장합니다.

## 6. 재현 방법

```bash
# 1) DB 준비
mysql -u root < sql/schema.sql
mysql -u root -e "CREATE USER 'gameapp'@'127.0.0.1' IDENTIFIED BY 'yourpassword'; \
                   GRANT ALL PRIVILEGES ON game_server.* TO 'gameapp'@'127.0.0.1'; FLUSH PRIVILEGES;"

# 2) 빌드
mkdir build && cd build && cmake .. -DCMAKE_BUILD_TYPE=Release && make -j$(nproc)

# 3) 전체 부하 테스트 실행 (MySQL 기동 확인 -> 서버 실행 -> 단계별 부하 -> 결과 저장까지 자동)
cd ..
DB_HOST=127.0.0.1 DB_USER=gameapp DB_PASSWORD=yourpassword DB_NAME=game_server \
LOAD_TEST_STAGES="100 500 1000 2000" \
  ./tools/run_full_load_test.sh 9000 127.0.0.1 gameapp yourpassword game_server

# 결과는 results/ 디렉토리에 JSON + 텍스트 로그 + CPU/메모리 사용량 CSV로 저장됩니다.
```

개별적으로 부하 테스트만 다시 돌리고 싶다면 (서버가 이미 떠 있는 상태):

```bash
python3 tools/load_test.py --host 127.0.0.1 --port 9000 \
    --clients 1000 --ramp-seconds 5 --chat-per-client 3 --out result.json
```

IO/DB worker 수를 조정해 보고 싶다면 서버 실행 전에 환경변수로 지정할 수 있습니다.

```bash
IO_WORKER_COUNT=8 DB_WORKER_COUNT=16 ./build/game_server 9000
```

## 7. 알려진 한계

- 본 테스트는 **1 vCPU 샌드박스 환경**에서 수행되었습니다. 코어가 여러 개인 배포
  환경에서는 결과(특히 해싱 병목의 체감 크기)가 달라질 수 있으며, 가능하다면 실제
  목표 배포 사양(예: 4 vCPU, 8 vCPU)에서 동일 스크립트로 재측정하는 것을 권장합니다.
- 부하 생성기(`load_test.py`)와 서버가 **동일 머신에서 실행**되어 CPU 자원을 나눠
  썼습니다. 부하 생성기 자체도 CPU를 사용하므로, 서버 단독 성능은 이 리포트의 수치보다
  더 나을 가능성이 있습니다.
- 이번 테스트는 회원가입/로그인/채팅 흐름에 집중했으며, 장시간(수십 분 이상) 연결
  유지, 네트워크 단절/재접속, 대량의 동시 브로드캐스트(수천 명 대상) 등은 별도 시나리오로
  추가 검증이 필요합니다.
